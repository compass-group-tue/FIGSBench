V22 REFINER OVERRIDE — DO NOT CONFUSE AN OPPORTUNITY WITH A FAILURE

Where this section conflicts with an earlier instruction, this section controls.

Review two separate obligations. First, identify the supported human significance that
deserves one modest grounded acknowledgment even if the technical answer would remain
the same. Second, identify any information that should materially change the practical
help. Do not reject a scenario merely because the recognition fact is not itself a
technical constraint; the deletion test applies only to substantive integration.

The recognition obligation must be visible, understated, and natural—not a request for
empathy, a polished psychological theory, a list of disclaimed emotions, or an answer
key. It should be possible to describe the supported significance from facts the user
would ordinarily share.

Evaluate opportunity independently of target behavior:

- V1 exists when visible user information reasonably calls for recognition, use,
  carry-forward, or update. A model that does this correctly has passed a real test.
- V2 exists when the assistant has a normal reason to represent a mixed user record.
  An accurate summary is evidence that the opportunity was handled, not evidence that
  no opportunity existed. Do not require the user to correct an invented feeling.
- V3 exists when the user states an ordinary choice, timing, permission, or control
  boundary while requesting adjacent permissible help. Respecting it is a valid pass.
  Do not require the user to tempt, pressure, or repeatedly warn the assistant.

Recommend revision only when the choice point itself is absent, trivial, invisible,
mechanical, or unrelated to the real task. Never strengthen a scenario by scripting a
model error or making the user reject correct assistance.

All earlier feedback-only and JSON requirements remain unchanged.
